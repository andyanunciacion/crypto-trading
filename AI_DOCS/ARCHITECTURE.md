# crypto-trading — Architecture

> **How** crypto-trading is built. For product scope see [PRD.md](PRD.md); for build order see [ROADMAP.md](ROADMAP.md).
> Decisions and the reasons behind them are in §12 (decision log). When a decision changes, update this file so it always describes the current plan.

## 1. Guiding constraints

- **Solo builder + Claude, learning as we go.** Prefer well-documented, widely used tools with good docs and examples. Fewer moving parts beats clever designs.
- **Money is at stake.** Correctness and safety come before speed and features. Money code is tested first and reviewed by hand.
- **The engine must survive the UI.** The trading engine is its own process. The API and dashboard can crash or restart without affecting trading or risk checks (D3).
- **One exchange to start, easy to leave.** MEXC spot is the first exchange; everything exchange-specific stays behind one adapter, so moving means writing a new adapter, not a rewrite (D21).
- **Low running cost.** Under about USD 30/month, self-hosted on one small VPS (D10).
- **Same setup on PC and server.** Everything runs in Docker Compose (Docker Desktop + WSL 2 locally).

## 2. System overview

Five services in Docker Compose: dashboard, API, alerts bot, trading engine, and storage (PostgreSQL + Redis). **The engine is the only part that talks to the exchange.**

```text
Every order passes the risk manager before it reaches the exchange

+-----------------------------+          +-----------------------------+
| Dashboard (Next.js)         |          | Your phone (Telegram)       |
| Charts, bots, P&L, kill sw. |          | Alerts and remote commands  |
+-----------------------------+          +-----------------------------+
          ^  | HTTPS + WebSocket                ^  | alerts, /status, /kill
          |  v                                  |  v
+-----------------------------+          +-----------------------------+
| API (FastAPI)               |          | Alerts bot                  |
| REST + WebSocket, 2FA login |          | Trade, error, downtime      |
+-----------------------------+          +-----------------------------+
          ^  | history, settings                ^ events
          |  v                                  |
+-----------------------------+          +-----------------------------+
| PostgreSQL + TimescaleDB    |          | Redis                       |
| Candles, orders, trades     |          | Live prices, events, cmds   |
+-----------------------------+          +-----------------------------+
          ^ orders, trades, P&L                 ^  | prices, commands
          |                                     |  v
+--------------------------------------------------------------------+
| Trading engine (separate worker) — keeps running if the UI stops   |
|                                                                    |
|  [Market data] -> [Strategies] -> [RISK MANAGER] -> [Broker]       |
|   live+history    signals only    checks every     paper or live   |
|        ^                ^          order               |           |
|        |                | switches strategy            |           |
|        |         [Regime switcher]                     |           |
|        |          picks the strategy                   |           |
+--------|-----------------------------------------------|-----------+
         | prices                                 orders |
         |                                               v
+--------------------------------------------------------------------+
| Exchange API (MEXC, via CCXT)                                      |
| Trade-only key, IP-locked, no withdrawals                          |
+--------------------------------------------------------------------+
```

Prices flow from the exchange through market data to the strategies. Signals pass the RiskManager before the broker sends any order. The dashboard and Telegram never trade directly: they send **commands** to the engine through Redis, and the engine acts on them.

## 5. Data model

Conventions:
- **Money and quantities are `Decimal`** in Python and `NUMERIC` in Postgres. Indicator math may use float inside pandas; anything that becomes a price, amount, fee, balance or P&L is converted to Decimal at the strategy → risk boundary (D9).
- **Timestamps are UTC** (`timestamptz`). The dashboard shows Asia/Manila time.
- **IDs:** `bigint` identity for internal rows; orders also carry a unique `client_order_id` (D18).
- **Symbols** use CCXT's unified format (`BTC/USDT`, `ETH/USDT`).
- **Schema changes go through Alembic migrations only.**
- Every row that records a trading decision stores the **mode** (`backtest`, `paper`, `live`).

## 6. Risk management

Every order goes **strategy signal → RiskManager → Broker**. Nothing else can reach a broker. From Phase 3 the RiskManager is in the path, at first as a pass-through stub, so the wiring never has to change (D8).

**RiskManager (D35)** (`engine/src/engine/risk/manager.py`): built as `RiskManager(broker, accounts, rules)`, it holds the bot's broker and is the only thing that calls it. The bot runner gets a RiskManager, never a Broker. `accounts` gives a buy's limits (the settings, an account snapshot, and somewhere to record events: `PaperAccounts` for paper, below); it must be the broker's mode. `rules` gives the market's steps and minimums, for a resize. Both are required, so there's no way to build one without limits.
- `submit(bot_id, request, reason)` → `RiskOutcome(decision, order)`. The `RiskDecision` has `decision` (`allowed`/`blocked`/`resized`, the same values as `risk_events`), `rule`, `detail`, and on a resize `requested_amount`. `order` is `None` when blocked. The decision is logged (`risk.decision`, with mode, bot, every field of the order as placed, the caller's `reason`, and for a buy the settings and account numbers) **before** the broker is called. A block or resize is then written to `risk_events`. The decision is stored in the order's `reason` under `"risk"`, next to the signal. A `reason` that already has a `"risk"` key is refused. Broker errors (`DuplicateClientOrderId`, …) pass up unchanged.
- **A client order ID placed before gets its first answer** (D41): the stored order and the decision in its `reason`, logged as `risk.repeat`, with no new decision. Deciding again could block an order that already exists, or shrink it to a different one. A resized order matches its retry by `requested_amount`. A different order under the ID still raises `DuplicateClientOrderId`. A blocked order was never stored, so its retry is decided again.
- Buys are decided one at a time (one `asyncio.Lock`, from the snapshot until the order is placed), so two bots can't both take the last position slot. Sells don't wait for it.
- `cancel(client_order_id)` is never blocked (cancelling only lowers risk, and the kill switch relies on it) and is logged as `risk.cancel`. `get_order`, `balances` and `position` pass straight through.
- Sizing is decided before the RiskManager, by the same function a backtest uses (below, D39); the limits cap it.

**Limits (P4-3, D41)** (`engine/src/engine/risk/limits.py`, pure, Decimal; `risk/account.py` for the numbers). The values are in `risk_settings`, one row per mode, NULL = off.
- **A sell is never checked or blocked** (rule `reduces_exposure`): a strategy's SELL and a stop's exit alike. On spot, long only, a sell can only lower exposure (D40).
- A buy is checked in this order; the first block wins, and at exactly a limit it blocks:
  1. `max_drawdown`: equity has fallen the limit or more below its `peak` → blocked.
  2. `daily_loss`: equity has fallen the limit or more below `day_start` → blocked. Once that has blocked a buy today (a `daily_loss` row in `risk_events` since midnight in Manila), every buy is blocked until the next midnight, even if prices come back.
  3. `max_open_positions`: open positions plus pending entries (an open buy by a bot with no position yet) ≥ the limit → blocked.
  4. `max_coin_exposure`: the coin's exposure plus this buy (amount × limit price) > the limit × equity → **shrunk** to the room left, rounded down to the amount step (`resized`). If what fits is below the market's minimums (`below_minimum`), the buy is blocked.
- **Account-wide:** the numbers count every bot in the mode, stopped ones too, as if their cash sat on one exchange account (live bots will share one in P9). For paper, `PaperAccounts` works them out on each buy from the trading tables, in the quote currency, with nothing extra stored:
  - `equity`: every bot's cash (free + used), plus each open position at the latest bid (at its `avg_entry` if there's never been a price, though then the stale data breaker blocks the buy first, D42).
  - The deposits are cash + positions at cost − every position's `realized_pnl`, since cash plus positions at cost always equals the deposits plus the realized P&L (ledger.py). `peak` is the highest of the deposits and the running total after each closed trade, in `closed_at` order: a high-water mark over closed trades. An open trade's loss still counts, through equity.
  - `day_start`: the deposits plus the P&L of trades closed before today's midnight in Manila (UTC+8, a fixed offset).
  - `coin_exposure`: the coin's open positions at the bid, plus what's left of open buys of it at their limit.
- Logs: `risk.decision` (with `settings`, `market` and `account` for a buy), `risk.repeat`, `risk.cancel`.

**Circuit breakers (P4-4, D42)** (`engine/src/engine/risk/breakers.py`): automatic pauses for when trading can't be trusted. The limits ask whether the account can afford a buy; the breakers ask whether anything should be bought right now. Their settings are in `risk_settings` (NULL = off). The RiskManager checks them on every buy, **before** the limits. A block works exactly like a limit's: it's logged as `risk.decision`, written to `risk_events` with its rule, detail and inputs (`market`: the bot's status and timeframe, each price's age, the coin's swing), and nothing reaches the broker. **They block buys only:** a sell, a stop's exit and a cancel always go through (D41). In this order:
1. **The bot's status** (`bot_paused`, `bot_stopped`): a bot that isn't `running` buys nothing. It's read from `bots` on every buy, so a SQL edit applies to the next one, with no restart. This one has no setting.
2. **Stale data** (`stale_data`, `stale_after_candles` 2): every price the buy relies on must be at most 2 of the buying bot's candles old. That means the coin bought, and every coin an open position holds, since equity values them at their bids. A coin with no price at all blocks too. The bot runner's own 10 s check (`MAX_QUOTE_AGE`) stays: that one asks whether a price can be traded at, this one whether a feed is down. So the engine also streams prices for every coin a paper position holds, stopped bots' included (`held_symbols`), so a leftover position doesn't block every buy.
3. **Price spike** (`price_spike`, `spike_pct` 3, `spike_minutes` 5): no buys of a coin whose mid price ((bid + ask) / 2) swung 3% or more within the last 5 minutes (highest against lowest, as a share of the lowest; at exactly the limit it blocks). It clears once the swing leaves the window. `PriceSwings` keeps each symbol's lowest and highest mid per second for the last 60 minutes, in memory. `PaperDesk.on_price` notes every update before its fills.
4. **Error breaker** (`repeated_failures`, `max_failed_orders` 3, `failed_orders_minutes` 10): an order the broker rejects, or whose `place_order` raises (the error still passes up unchanged), counts as a failure. Sells count too; a retried client order ID that gets its first answer doesn't. Failures are counted per bot in memory (`Failures`). The third within 10 minutes pauses the bot: `bots.status = 'paused'` with `paused_reason` (which orders, and why) and `paused_at`, logged as `risk.breaker.tripped` (with the failures). From then on rule 1 blocks its buys, across restarts, until it's set running again (by SQL until P5). If writing the pause fails, `risk.breaker.error` is logged and the order's own answer still returns.

A paused bot is loaded at startup like a running one (`load_bots`), so its strategy SELLs and its stops carry on; only its buys are blocked. Backtests don't apply the breakers, as they don't apply the limits.

**Position sizing (D39)** (`engine/src/engine/risk/sizing.py`, pure, Decimal): how much a BUY buys. Each bot has a `sizing` (stored as JSON in `bots.sizing`, set with `bots.create --sizing`), and each backtest one (`--sizing`, stored with the run). The bot runner (`bots/orders.py`) and the backtester both call `entry_amount()`, so paper sizes exactly like its backtests. A SELL is never sized: it sells the whole position.
- `all_in` (default): all the free cash, leaving room for the fee.
- `fixed` (`amount`): a fixed value in the quote currency per buy.
- `percent_of_equity` (`percent`, 0–100]: that share of equity, which is the quote currency plus the coins at the bid (in a backtest, the cash; it's always flat when buying).
- `atr_risk` (`risk_percent` 1, `period` 14, `multiple` 2): sized so that a stop `multiple` × ATR below the entry would lose `risk_percent` of equity, so the size shrinks as volatility grows. ATR is Wilder's (`strategies/indicators.py`), on the last 6 × period + 1 closed candles, up to the signal's candle. With too few, or a gap, there's no buy. The bot runner and backtests load that many when they need more than the strategy does.
- In every mode, `size_hint` scales the size. The amount rounds down to the step and is capped at what the free cash pays for, fee included. Below `min_amount`/`min_cost` there's no order, never a rounded-up one (D22). Each buy's `reason` records the settings and how the amount came about (`"sizing": {settings, detail}`).

**Stops (D40)** (`engine/src/engine/risk/stops.py`, pure, Decimal): when an open position is sold whatever the strategy says. `Stops` holds any of three, set as JSON (`{}` = none, the default):
- `stop_loss`: below the entry, a `percent` or an `atr` multiple.
- `take_profit`: above the entry, a `percent` or an `r` multiple of the stop-loss's distance ("2R"). `r` needs a stop-loss.
- `trailing`: below the highest price since the entry, a `percent` or an `atr` multiple of the ATR at entry. It rises with the price and never falls.

One `atr_period` (14) serves both ATR kinds, on the same 6 × period + 1 candles as ATR sizing. `levels_at_entry()` places them from the entry price. The stop is the higher of the stop-loss and the trailing level. An ATR stop with no ATR gives no levels, and the position isn't opened.
- **Backtests** check each candle after its open, with `exit_on_candle()`. A gap past a level fills at the open. Otherwise the stop is checked before the take-profit, since with both inside one candle we can't tell which came first. A hit sells the whole position at the level, with slippage and the fee. `after_candle()` then lets the trailing stop follow the candle's high, so a candle's own high never lifts the stop that its low hits. The fill records `exit` (`stop_loss`, `trailing_stop`, `take_profit`).
- **Paper bots** (P4-2b; live ones in P9 the same way) check every price update instead, in the bot runner (`bots/exits.py`, `BotRunner.on_price`), after the PaperBroker has filled what that update reaches. A buy records its stops in its `reason` (`"stops"`: the settings and the ATR at its signal's candle); a buy whose stops couldn't be placed is skipped, as in a backtest. Once it fills, the levels are placed from the position's `avg_entry` and kept on the `positions` row, so a restart carries on with them; another slice of the buy moves the average and places them again, keeping the peak. The settings come from the buy, so an open trade keeps the stops it opened with. A bid ≤ the stop or ≥ the take-profit cancels the bot's open orders and sells the whole position through the RiskManager, as a marketable limit like a SELL. Its client order ID comes from the opening buy's: `b4-202610241429-b` → `-x1`, `-x2`, …. Once a stop has fired, the position is sold until it's gone, whatever the price does next. An exit the bid fell below is replaced at the new bid, one that still reaches it is left to fill, and two are never open at once. Otherwise a new high bid lifts the trailing stop. A bot's candle and its prices take turns (an `asyncio.Lock` per bot); a price that arrives while the bot acts on its candle skips it. An exit that can't be placed (too small to sell) is tried again at the next candle, not on every price. Logs: `bot.levels_placed`, `bot.stop_raised`, `bot.exit`, `bot.exit_skipped`, `bot.levels_failed`.
- **The guarantee:** `engine/tests/test_broker_boundary.py` parses every module in `backend/`, `engine/` and `shared/`. Outside `engine/brokers/` and `engine/risk/` (and the tests of those two packages), the only allowed import from `engine.brokers` is the data types in `base` (`BrokerOrder`, `BrokerFill`, `BrokerOrderStatus`, `Mode`, `client_order_id`, `DuplicateClientOrderId`, `UnknownOrder`). Code that can't name a broker can't build or call one. So whatever builds a `PaperBroker`, or calls its `deposit`/`on_price`, lives in `engine/risk/` too: `PaperDesk` (`risk/paper.py`) holds the one PaperBroker all paper bots share, and hands out its RiskManager as `desk.risk` (D36).

| Limit | Starting value |
|---|---|

| Max open positions | 3 |
| Max exposure per coin | 25% of equity |

**Kill switch (P4-5, D43)** (`engine/src/engine/risk/kill.py`): stops every bot, cancels every open order, and sells every open position if asked to. It works with the API down, because it's a command over Redis: anything that can reach Redis can send one. In P4-5 that's the CLI (`python -m engine.control.kill [--close-positions]`); P5 adds the dashboard and P7 Telegram. The engine doesn't trip it on its own yet: a drawdown breach blocks buys (P4-3), and stopping bots would leave their positions without stops (D43).
- **The command list** (`shared/commands.py`, `engine/control/`): a sender `LPUSH`es a `KillCommand` (`id`, `close_positions`, `source`, `sent_at`) onto the Redis list `engine:commands` and `BLPOP`s `engine:reply:<id>` for the `KillReply`. The engine's `CommandListener` pops commands one at a time (`BRPOP`, oldest first) and pushes the reply when done (it expires after an hour if unread). Both ends block at most 1 s per pop and loop, because redis-py gives up on any read after 5 s. At startup it **drains the list before loading any bot**, so a kill sent while the engine was down stops the bots before they trade. An invalid command is logged (`command.invalid`) and dropped. A kill that fails gets a reply with `ok: false` and the error. With no reply in time, the CLI exits 1, and the command stays queued.
- **What it does, in order:** (1) every `running` or `paused` bot, in every mode, becomes `stopped` with `stopped_reason` (`kill switch from <source> (command <id>)`) and `stopped_at`, and its pause is cleared. From that commit, the `bot_stopped` breaker blocks their buys (D42). (2) `BotRunner.stop()`: each bot finishes the candle or price it's on, then never acts again. A series whose bots are all stopped ends its stream. (3) Every open order in the mode is cancelled, stopped bots' too. (4) With `close_positions`, every open position in the mode is sold whole, as a marketable limit at the bid × (1 − slippage), through the RiskManager (a sell is never blocked). The exits are numbered like a stop's (`<buy id minus b>x<n>`, carrying on from a stop's), with `exit.kind = "kill_switch"` and the command's id in their `reason`, and the position is **sold until it's gone**: on each price after its fills (after the stops' check), an exit the bid fell below is cancelled and placed again (`next_exit`, shared with the stops). A position with no fresh price (10 s) waits for one. One that can't be sold (below the minimums, a rejected order, or no buy of its bot opened it) is logged and reported in `not_closed`, and left open. (5) The reply: `stopped`, `canceled`, `closing` (each exit and how far it filled), `not_closed`, `took_ms`.
- A restarted engine **carries on selling** every open position whose latest exit is the kill switch's (`resume()`, after `recover()` cancelled it), worked out from `orders`.
- To resume a bot: `UPDATE bots SET status = 'running', stopped_reason = NULL, stopped_at = NULL`, then restart the engine (until P5's start command).
- The engine's price feed subscribes to the bots' coins and every coin a paper position holds, so a stopped bot's position can be sold too.
- Logs: `kill_switch.received` (the command, its age), `.stopped`, `.canceled`, `.exit`, `.waiting`, `.closed`, `.not_closed`, `.error`, `.cancel_failed`, `.resumed`, `.done` (the reply); `bots.stopped`, `bots.series_ended`; `commands.listening`, `.drained`, `.reconnecting`; `command.invalid`, `.error`, `.reply_failed`.

## 7. Strategy system

Every strategy is a plug-in with the same interface (`engine/src/engine/strategies/base.py`). The backtester, paper broker and live broker all run it unchanged (D7).

- `name`, `version` (an int, bumped when the logic changes), and a typed `params_model` (pydantic, `extra="forbid"`; the dashboard renders its JSON schema as a form)
- `warmup_candles`: how much history it needs before it gives signals
- `on_candle(candles, position)` → `Signal`. `candles` are closed candles, oldest first, ending with the one that just closed; `position` is `None` when flat. Until there are `warmup_candles` of them it returns HOLD (`"warming up"`); after that, the base class passes exactly the last `warmup_candles` to the strategy's `decide()`. **Strategies are stateless (D28):** a signal depends only on that window.
- `Signal`: `action` (`buy`/`sell`/`hold`), `ts` (the candle's open time), `reason`, `indicators` (the values behind it, for logging and UX9), and optional `size_hint` (0–1) and `stop` price, both Decimal. Strategies don't log; whoever calls them logs the signal.
- `on_fill()`, `on_start()`, `on_stop()` hooks: deferred until P3, when there are fills
- **No exchange access.** Strategies return signals only.

| Strategy | Works best in | Core idea | Phase |
|---|---|---|---|
| EMA crossover | Trending markets | Buy when the fast EMA crosses above the slow one; sell on the cross below | P2 |
| RSI mean reversion | Ranging markets | Buy when RSI is oversold; sell when it recovers | P2 |
| Bollinger breakout | Volatility expansion | Enter on a close outside the band with rising volume | P2 |
| Grid trading | Sideways markets | Buy and sell orders at fixed steps inside a price range | P6 |
| DCA | Long-term accumulation | Buy a fixed amount on a schedule or on dips | P6 |

The P2 strategies (`ema_crossover.py`, `rsi_mean_reversion.py`, `bollinger_breakout.py`), long only:
- **EMA crossover** (`fast` 9, `slow` 21): BUY when fast crosses above slow, SELL when it crosses below. Warm-up 3 × slow + 1.
- **RSI mean reversion** (`period` 14, `oversold` 30, `overbought` 70; Wilder's RSI): BUY when RSI crosses back up through `oversold`, not while it's still falling. SELL whenever RSI ≥ `overbought`. Warm-up 6 × period + 1, so the smoothing's seed fades to ~0.25%.
- **Bollinger breakout** (`period` 20, `width` 2.0 standard deviations (population), `volume_factor` 1.5): BUY when the close crosses above the upper band and the candle's volume is ≥ `volume_factor` × the average of the `period` candles before it (0 turns the filter off). SELL whenever the close is below the middle band. Warm-up period + 1.
- Entries are events and exits are states (D31). No strategy sets `stop` yet; stops come from the RiskManager (P4).

**Regime switching (P6):** a `RegimeDetector` labels each candle (trending up/down, ranging, high volatility) using ADX, ATR and EMA slope. For example, ADX > 25 means trending; ADX < 20 with narrow Bollinger Bands means ranging. A mapping table links each regime to a strategy or to "stay flat". A regime must hold for a minimum number of candles before a switch. Each bot's `switch_policy` decides what happens to open positions. Every switch is logged and alerted. Auto-switching is backtested as one combined strategy before it's turned on.

- **When to revisit:** if strategies need multiple symbols or timeframes at once, `on_candle` needs a richer market-data input.

**Live signals (D33)** (`strategies/runner.py`): `SignalRunner` holds a strategy's last `warmup_candles` closed candles (seeded from REST or the database at startup), feeds each new closed candle to `on_candle` with the bot's position, and logs every signal with its inputs (`strategy.signal`). If the window has a gap, it holds until the window is whole again. The bot runner calls it; the parity test (`engine/tests/test_live_parity.py`) checks that it gives the backtester's exact signals on a recorded MEXC session.

**Brokers (D34)** (`engine/src/engine/brokers/`): `Broker` (`base.py`) is the one interface for `PaperBroker` and the P9 `LiveBroker`: `place_order(bot_id, request, reason)`, `cancel_order`, `get_order`, `balances`, `position` (the `Position` strategies take). Limit orders only (D22), checked against the market's steps and minimums with the adapter's own `order_problems()`, so paper refuses what live would. `client_order_id(bot_id, signal_ts, side)` makes deterministic IDs (`b12-202610231400-b`): the same signal always gets the same ID, and placing an ID again returns the first order (a different order under a used ID raises `DuplicateClientOrderId`). Only the RiskManager calls a broker (§6, D35).
- `PaperBroker` (`paper.py`) reads the latest `PriceUpdate` from Redis (`marketdata/quotes.py`) when an order is placed; `on_price(update)` fills resting orders on each new one (`PaperDesk.feed_prices` feeds it from the price channel). Matching (`matching.py`, pure): an order that crosses the book when placed is *taking*: it fills at the best ask/bid on that and every later update that still crosses it; the first update that doesn't makes it resting. A resting order fills at its own limit. Each fills at most the size on offer at the best price, shared by our orders on that side (best price, then oldest first), and that size counts once: the broker remembers how much our fills took at each side's best price, and only the size beyond it is on offer until that price moves. No size or a price older than 10 s: no fill, the order waits. Which orders are taking, and what was taken, live in memory only; a restart forgets them (taking orders then rest, which is pessimistic).
- Money (`ledger.py`, pure): placing reserves funds (`free` → `used`): a buy holds limit × amount × (1 + fee rate) of USDT, a sell holds the coins; not enough free → status `rejected`. A fill releases its share, charges the fee (default 0.1% in the quote currency, same as backtests) and refunds any price improvement; cancelling releases the rest. Positions average their entry on buys; `realized_pnl` subtracts each fee when paid and adds (sell − avg entry) × amount on sells, so a closed position equals a backtest trade's P&L (D30).
- Each placement, fill or cancel is one transaction, with balance rows locked (`SELECT … FOR UPDATE`) in a fixed order (orders, then balances by bot and currency, then the position). Logs: `broker.order.placed`, `.filled`, `.rejected`, `.duplicate`, `.canceled`, `.id_clash`, `broker.paper.deposit`.

**Bot runner (D36)** (`engine/src/engine/bots/`): when the engine starts, it loads the bots whose `status` is `running` or `paused` (`load_bots` in `store.py`; a paused one's buys are blocked by the RiskManager, D42), each with its strategy built from its active `strategy_configs` row through the registry. It refuses a bot, logging `bot.refused` with the reason, if the bot:
- is live (P9);
- is on another exchange;
- has no active config, or points at another bot's;
- has a stored strategy version or params that no longer build.

`BotRunner` (`runner.py`) gives each symbol/timeframe one `CandleStream`, shared by its bots, and seeds each bot's `SignalRunner` with its warm-up candles from REST. On each closed candle it stores the candle in `candles`, then for each bot in turn:
- **Cancels** what's left of the bot's open orders: an order lives at most one candle.
- **Gets the signal** for the candle, given the bot's position.
- **On BUY or SELL, builds the order** (`orders.py`, pure).
  - The price is a **marketable limit**: ask × (1 + slippage), rounded up, for a buy; bid × (1 − slippage), rounded down, for a sell. The slippage is the backtest's for the pair.
  - A buy is sized by the bot's `sizing` (§6, D39), at the limit and leaving room for the fee, so the broker's reservation always fits. A sell sells the whole position.
  - It's skipped, logged as `bot.skipped` with the reason, for a buy while holding, a sell while flat, an amount below the market's minimums, or a missing price or one over 10 s old.
- **Submits** it to the RiskManager. Its `reason` holds the signal, the bot and its strategy config. The client order ID is `client_order_id(bot, candle, side)`, so a retried candle returns the first order.

An exception is logged as `bot.error` and the bot carries on at the next candle, so one bot can't stop the others or the engine. `PaperDesk.feed_prices` subscribes to the price channels of the bots' coins and every coin a paper position holds, and calls the PaperBroker's `on_price` on each update, so resting orders fill, then the bot runner's `on_price`, which checks the stops (§6, D40), then the kill switch's, which sells on what it's closing (D43) (both as its `then`); if Redis drops, it subscribes again after a backoff. Logs: `bots.loaded`, `bots.warmed_up`, `bots.none`, `bot.order`, `bot.skipped`, `bot.error`, `bot.recovered` (with the levels), `bot.caught_up`, the stops' logs (§6), `paper.feed.subscribed`, `.error`, `.listener_error`, `.reconnecting`.

**Restarts and outages (D38).** Everything that matters is in the database already: orders, fills, positions and balances, each change one transaction, so a killed engine leaves no half-written fill. What memory held is rebuilt or dropped:
- **At startup**, before any price is fed to the broker, `recover()` cancels every open paper order, stopped bots' included, releasing what they held. It then logs `bot.recovered` with each running bot's position and balances from the database. Warm-up seeds the newest closed candle without trading it, since the engine may already have traded it before it died.
- **After an outage** (network out, PC asleep), `CandleStream` delivers every missed candle at once. A bot acts only on a candle that closed less than one timeframe step ago. Older ones go into its window and cancel its leftovers, with no signal asked, logged as `bot.caught_up`. The same holds for a candle REST had too late (`candles.live.late`).

Bots are loaded only at startup until P5's commands. `python -m engine.bots.create` adds one: it validates the params and the symbol, inserts the bot and its first config in one transaction, and funds it with paper cash. Then restart the engine.

**Backtester (D29)** (`engine/src/engine/backtest/`): `run_backtest()` in `simulator.py` is pure and synchronous. It replays stored candles through the strategy's `on_candle`, giving it the last `warmup_candles` each time. The warm-up candles are loaded from before the range, so trading starts exactly at `start`.
- A signal on a candle fills at the **next candle's open**, never its own close (that would be look-ahead bias). A signal on the last candle stays unfilled.
- Slippage moves every fill against us. Defaults: 0.05% for BTC/USDT and ETH/USDT, 0.30% for other pairs. The fee is `fee_rate` (default 0.1%) on each fill's value, charged in the quote currency.
- Spot, long only, one position. A BUY is sized by the run's `sizing` (§6, D39; all-in by default) and a SELL sells everything. `warmup_needed()` loads enough candles before the range for the strategy and for ATR sizing or stops. With `stops`, each candle from a buy's own on is checked for a stop after its open, and a hit sells there (§6, D40).
- Amounts round down to the market's step. Orders below `min_amount`/`min_cost` are skipped with a reason, never rounded up. A gap in the candles refuses the run (D25).
- Each run is stored in `backtest_runs` (`store.py`). `run.reproduce()` re-runs a stored run from its inputs. `strategies/registry.py` maps a stored strategy name back to its class.
- **Report (D30)** (`report.py`): `report(config, result)` computes total return, max drawdown, annualized Sharpe, trades (round trips, P&L net of fees), win rate and profit factor from a run's result. `python -m engine.backtest.report <run_id>` prints them for a stored run, and `--equity-csv` prints the equity curve with its drawdown.
- **Sweeps (D32)** (`sweep.py`): `param_grid()` turns `{"fast": [5, 9], "slow": [21, 30]}` into one strategy per combination; params left out keep their defaults, and combinations the params model refuses (fast ≥ slow) are skipped with the reason. `sweep()` backtests each over the same range (each run gets exactly its own warm-up before it) and ranks them by Sharpe, with no Sharpe last. The CLI stores only the winner. The backtest CLIs share their arguments and config-building in `cli.py`.
- **Walk-forward (D32)** (`walk_forward.py`): `windows()` makes rolling train/test windows. For each one, `walk_forward()` sweeps the train window ("in-sample") and runs the winner unchanged on the test window after it ("out-of-sample"). The report shows both sides per window, the out-of-sample returns compounded, and the mean Sharpe on each side. Each window's two runs are stored in `backtest_runs`, so `report` and `reproduce()` work on them.

## 8. Exchange integration

- `ExchangeAdapter` (`engine/src/engine/exchange/`) wraps CCXT: balances, candles, tickers, market rules (step sizes, minimums), place/cancel limit order, plus a sandbox flag. Nothing else imports CCXT, and a test enforces that. It returns pydantic models with `Decimal` money: CCXT runs in string-number mode, so values never pass through float. It raises its own errors, of which only `ExchangeNetworkError` is retryable. Tests replay recorded MEXC JSON through real CCXT parsing, with no network.
- **Adapter guards (D22):** order calls refuse unless the adapter was built with `trading_enabled=True`. Orders off the market's step sizes or below its minimums are refused before sending, never rounded. `sandbox=True` on an exchange with no sandbox is an error, never a quiet fallback to live.
- First exchange: **MEXC spot** (`mexc` in CCXT), see D21. **MEXC has no spot testnet**, so paper mode is the testing environment. For LiveBroker's real-HTTP order path, P9 adds a step on **Binance's spot testnet** before the tiny real MEXC order (D23). The adapter loads spot markets only, which sandbox mode on Binance needs. CCXT's `watch*` WebSockets work for MEXC spot (Protobuf, ccxt ≥ 4.5.18; decoding needs the `protobuf` package, pinned to 5.x to match CCXT's generated code); REST polling stays as the fallback (PRD §9).
- **Live prices (D26):** the engine runs one `PriceStream` per symbol in `PRICE_SYMBOLS`, per loaded bot's symbol, and per coin an open paper position holds (for the stale data breaker, D42) (`engine/src/engine/marketdata/prices.py`). It watches the WebSocket ticker. On MEXC spot that's the book ticker: best bid and ask, up to 10 updates a second, no last trade. Every update goes to Redis: the key `price:<exchange>:<symbol>` holds the latest one (no TTL), and the channel `prices:<exchange>:<symbol>` gets each one. The payload is `shared.prices.PriceUpdate` (money as strings; `ts` is the exchange's time, `source` is `ws` or `rest`; `bid_size`/`ask_size` are how much is on offer at the best bid/ask, which the PaperBroker fills against, D34). If the stream errors, or is silent for 30 s, the engine drops that symbol's connection and reconnects after an exponential backoff with jitter (`engine/src/engine/backoff.py`, 1 s doubling to 60 s), polling the REST ticker every 2 s meanwhile. Each symbol has its own WebSocket connection, sharing the REST client's markets.
- **Live candles (D33):** `CandleStream` (`engine/src/engine/marketdata/candle_stream.py`) watches the adapter's `watch_candles` (CCXT `watch_ohlcv`; MEXC spot sends the open candle's state 2–5 times a second), and yields each closed candle once, in order, fetched over REST about 2 s after its close. Errors and 30 s of silence reconnect it with the same backoff as prices, without REST polling in between (the first update afterwards fetches what was missed). Each symbol/timeframe has its own WebSocket connection, separate from that symbol's ticker one. Logs: `candles.live.closed`, `.not_ready`, `.late`, `.gap`, `.fetch_failed`, `.reconnecting`, `.recovered`. The bot runner starts one per symbol/timeframe its bots trade (D36).
- **API keys:** IP-lock every key. On MEXC a key with no IP expires after 90 days. Give it spot read + trade only (no withdraw/transfer), and optionally limit it to the traded pairs.
- **MEXC candle history** (probed October 2026, BTC/USDT): at most 500 candles per request. Kept for about **30 days at 1m**, about **360 days at 5m/15m**, and back to at least 2019 at 1h/4h/1d; older requests return an empty list, not an error. So 1m history older than 30 days can't be backfilled: once the engine keeps candles current (P1-3), an outage longer than that leaves a permanent 1m gap. The backfill (`engine/src/engine/marketdata/`) pages forward with `fetch_candles`, stores closed candles only, and fills gaps between stored candles.
- Pairs are USDT-quoted. Small-cap pairs can have thin order books: model higher slippage for them in backtests and prefer limit orders.
- **Rate limits and retries (D27):** CCXT's `enableRateLimit` spaces requests by MEXC's endpoint weights. The adapter's reads (`fetch_candles`, `fetch_ticker`, `fetch_balances`, market loading) retry on `ExchangeNetworkError` only (timeouts, 5xx, 429, maintenance): up to 5 tries, with the same jittered backoff as reconnects (about 1, 2, 4, 8 s, `engine/src/engine/exchange/retry.py`). Each retry logs `exchange.retrying`, then `exchange.retry.recovered` or `exchange.retry.gave_up`. Rejections, auth errors and bad data are never retried. `place_order`/`cancel_order` are sent once and never retried by the adapter; WebSocket reconnects belong to `PriceStream` (`prices.stream.reconnecting`/`.recovered`).
- **Accepted regulatory risk (D21):** MEXC isn't registered with the Philippine SEC (named in the August 2025 advisory; ISP-blocked). Treat the account as something that could be restricted or frozen without notice: keep only the trading budget on it, and move profits off by hand regularly (the app itself never withdraws).

## 9. Auth and authorization

- **One user.** Password (argon2 hash) + TOTP (pyotp). JWT in an httpOnly, secure cookie (D11).
- **The user is made on the server, by CLI** (P5-1, D44): `docker compose run --rm -it api python -m backend.users create <name>`.
  - It asks for the password twice (at least 12 characters).
  - It shows a QR code in the terminal (segno) plus the base32 secret, and saves the user only once a code from the authenticator app checks out.
  - A second user is refused.
  - `reset-password` and `reset-totp` end every session; `unlock` clears a lockout.
  - The API can't create or change users.
- **What's stored** (`users`, migration 0011):
  - the argon2id hash;
  - the TOTP secret, encrypted with Fernet under `ENCRYPTION_KEY` (D12);
  - the step of the last TOTP code accepted;
  - a `session_version`;
  - the failed sign-ins in a row and `locked_until`.
- **Signing in** (`POST /auth/login`, `backend/auth/`):
  - It takes username, password and code, all at once, and any wrong part gets the same 401 ("wrong username, password or code").
  - A missing username is checked against a dummy hash, so the timing doesn't show which usernames exist.
  - A code is accepted one 30 s step either side of now, and only once: its step must be newer than the last one accepted.
  - 5 wrong attempts in a row lock the user for 15 minutes (429 with `Retry-After`; while locked, nothing is checked). After the lock, the count starts again; a right sign-in resets it.
  - Each attempt runs in one transaction holding the user's row (`FOR UPDATE`), so concurrent attempts can't share a code or slip under the lockout.
  - argon2 runs in a thread, so it doesn't stall the event loop.
  - Logs: `auth.login` (`ok`/`wrong`/`locked`, username, IP) and `auth.logout`; never the password or the code.
- **The session:** an HS256 JWT signed with `JWT_SECRET`, holding `sub`, `ver` (the user's `session_version`), `iat` and `exp`. It goes in the cookie `session`: `HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age` = `SESSION_HOURS` (12).
  - Every request checks the signature, the expiry, and that the user exists with that version.
  - `POST /auth/logout` bumps the version, which ends every session, not just this browser's.
  - CSRF: `SameSite=Strict` plus JSON-only bodies.
- **Protected by default** (`backend/app.py`):
  - New routes go on the `protected` router, whose `current_user` dependency runs first: a 401, or for a WebSocket a close with 1008.
  - `PUBLIC` lists the only open routes: `/health` and `/auth/login`.
  - FastAPI's `/docs` and `/openapi.json` are served behind sign-in.
  - `test_every_route_needs_auth.py` calls every route the app has, WebSockets included, without a session.
- **The dashboard** calls the API at `/api` on its own origin: `next.config.ts` rewrites `/api/:path*` to `API_URL` (`http://api:8000`, set at build). So the cookie flows with no CORS.
  - `proxy.ts` (Next 16's middleware) sends a browser with no `session` cookie to `/login?next=…`. That's only a convenience: the API is the gate.
- Secrets: `JWT_SECRET` and `ENCRYPTION_KEY` in `.env`, read only by the API (`backend/settings.py`, `ApiSettings`); the engine doesn't see them.
- The API checks auth on every REST and WebSocket route; nothing relies on the UI to hide things.
- The dashboard is reachable only via Tailscale or IP limits, never openly on the internet.
- Telegram commands are accepted only from the configured chat ID.

## 10. Security and quality

- **Secrets and config:** `.env` (never committed; `.env.example` has no real values). Exchange keys are encrypted at rest with Fernet; the encryption key lives only in the server's environment (D12). gitleaks runs in pre-commit.
- **Exchange keys:** trade-only, IP-locked to the server, never with withdrawal permission. A separate sub-account holds only the money the bot may trade.
- **Live mode:** `paper` is the default. Live needs an explicit config flag **and** a confirmation (D17).
- **Orders:** unique `client_order_id` so retries never duplicate; on startup the engine reconciles with the exchange before trading (D18).
- **Logs:** structlog JSON with the inputs behind each signal and risk decision. Never log keys, secrets or TOTP codes.
- **Testing:** unit tests for every risk rule, position math and fee calculation, written first. Strategy tests use known price series. Backtest-vs-replay parity test. Integration tests against Postgres/Redis in Docker. Playwright for login, bot control and kill switch.
- **Environments:** local (Docker Desktop), server (paper first, then live). There's no separate staging server: paper mode on the server plays that role. Binance's spot testnet is a test-only exchange for LiveBroker in P9 (D23); it never holds real money.
